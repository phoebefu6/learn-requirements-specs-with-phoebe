Part 1 · covers Given/When/Then

Given, When, Then

5 min live

Given, When, Then is a three-line shape for one example of the product behaving correctly. It forces the writer to separate the situation, the trigger and the result, and only the result is something the builder checks. Follow one Saffrondale scenario through the three lines and notice which part a tester actually looks at.

LiveThree keywords, three jobs3 min▶

The Cucumber Gherkin reference gives each keyword one job. Given is the initial context: the state of the world before anything happens. When is an event or action: the one thing the user does. Then is an expected outcome: what the user should now see.

The reference adds the rule that makes Then lines useful: you should only verify an outcome that is observable for the user, and avoid checking hidden internals such as database records. For a data product that is a sharp test. "The rate is stored correctly" is an internal. "The page shows last week's rate for that clinic" is an outcome someone can look at, and argue about, before launch.

The shape is older than the tools that run it. The Agile Alliance glossary describes Given-When-Then as "a template intended to guide the writing of acceptance tests for a User Story", and its user-stories page dates the template to 2006. The template is usually credited to Dan North and Chris Matts; that attribution is reported, because the glossary page itself does not name them.

★ One Saffrondale scenario (constructed)Given the dashboard is opened on a Monday When the clinic operations lead picks a clinic Then the page shows last week's no-show rate for that clinic, Monday to Sunday.
Self-studyThe full keyword list4 min▶

Given, When and Then are three of the keywords in the Gherkin reference. The full list, and what each is for:

KeywordWhat it does
FeatureNames the piece of the product the scenarios describe
RuleOne business rule, grouping the examples that illustrate it (Part 2)
Example / ScenarioOne concrete case, written as steps
Given, When, ThenInitial context, an event or action, an expected outcome
And, ButContinue the previous step without repeating its keyword

Gherkin can also be executed: test tools read the scenarios and run them against the product. That is a category of tooling, and none of it is needed here. Everything in these six sessions is about writing criteria a person could check by hand; whether a team later automates them is the builder's choice.

Real world

Check what the user can see. The Cucumber Gherkin reference is explicit that a Then step should verify an outcome observable for the user, and should avoid checking things like database records. For data products this is the line between "the pipeline ran" and "the number on the page is right". Only the second one is what the requester asked for (Cucumber, Gherkin reference, cucumber.io/docs/gherkin/reference).

Part 2 · covers rule-based and non-functional criteria

Rules, freshness, speed and access

5 min live

Not every criterion is a scenario. Some are business rules that need one worked example to be unambiguous. Others are about the product as a whole: how old the data may be, how fast the page opens, who may see what. These non-functional criteria are criteria too, and they are the ones most often left as adjectives. The trick is the same every time: write down the measurement a builder would take.

LiveRule-based criteria2 min▶

Some requirements are rules rather than journeys: who counts, what is excluded, which threshold applies. Since Gherkin 6, the reference has a Rule keyword for exactly this: one business rule, with the examples that illustrate it grouped underneath. The rule states the policy; the example removes the arguments about edge cases.

Saffrondale's no-show rate depends on one such rule (constructed): a patient who cancels 24 hours or more before the start time is not a no-show. Written alone, the rule still leaves room for doubt: 24 hours before what, measured from which timestamp? One example settles it.

★ A rule with its example (Constructed Saffrondale example)Rule: A patient who cancels 24 hours or more before the start is not a no-show Example: cancelled the day before Given a booking on Tuesday at 10:00 When the patient cancels on Monday at 09:00 Then the no-show list does not include that appointment

Monday 09:00 is 25 hours before Tuesday 10:00, so the cancellation is outside the window. Write the second example, a cancellation at 11:00 on Monday, 23 hours before, and the rule's edge is pinned on both sides. Session 5 puts the same rule into the metric definition itself.

LiveNon-functional criteria are criteria too3 min▶

Freshness, speed and access are about the whole product, not one story, and they are where adjectives hide: "up to date", "fast", "secure". Each has a measurable version:

Freshness. How old may the data be at the moment someone acts on it? "Data on the page is no older than 24 hours at 07:00 each weekday" names a deadline and an age. A builder checks it with a clock and the timestamp of the newest row.

Latency. How fast, under what load? "The page opens in under 3 seconds for 20 users at the same time" names both the number and the condition. Without the load, three seconds for one person on a quiet morning proves little.

Access. Who sees what? "A receptionist account shows only the patients of its own clinic" can be checked by logging in as two receptionists from two clinics and comparing.

Bill Wake's INVEST list puts it plainly: "A good story is testable" (Wake, 2003). Applying the same demand to the product-wide lines is our reading, not a sentence Wake wrote, but the logic carries: if nobody can say what would be measured, nobody can say whether it was delivered.

Self-studyWhat the checker counts as testable4 min▶

Session 4's spec checker cannot read meaning, so it uses a proxy. Its "Criterion with nothing to check" rule is lab-only, written for these sessions after Wake's Testable and Gherkin's advice on observable outcomes. A Then line (or an And or But after a Then), or any bullet under "Acceptance criteria:", passes when it carries at least one of:

  • a number (any digit),
  • a quoted value, such as "no-show",
  • an observable verb: shows, lists, returns, sends, flags, highlights, exports, equals, matches, appears, contains, includes, sorted, filtered, counts, prints, opens, alerts (and their simple forms, such as show or list).
CriterionChecker saysCould a person test it?
Only clinic leads can see phone numbers.Nothing to check: no digit, no quote, and "see" is not on the listYes: log in as a clinic lead and as a receptionist, and look
A receptionist account shows only the patients of its own clinic.Passes: "shows"Yes
The model works well.Nothing to checkNo: works well by what measure, on which patients?

The first row is the honest limit. A human could test it, and the checker flags it anyway, because the proxy is a word list. Treat the flag as a prompt to reread the line, not as a verdict: often a rewrite with an observable verb ("A receptionist account shows no phone numbers") is clearer for the builder too. And the proxy fails the other way as well: a line can contain "shows" and still say nothing measurable. The checker counts the words; you judge the meaning.

Real world

The requirement was written. Nobody checked the file against it. NASA's Mars Climate Orbiter was lost on 23 September 1999. The Mishap Investigation Board found that the Software Interface Specification required thruster impulse data in metric units, newton-seconds. The ground software file "SM_FORCES" produced pound-force seconds instead, and the trajectory modelers assumed metric "per the requirements". The small-forces delta-V was low by a factor of 4.45. The lesson for a spec writer is not that a requirement was missing: it was there, in writing. What was missing was a check of the delivered output against it. Acceptance criteria are how a written requirement gets checked (NASA, 1999, Mars Climate Orbiter Mishap Investigation Board Phase I Report).

Part 3 · covers the definition of done

Acceptance criteria and the definition of done

5 min live

Acceptance criteria say what this story must do. A definition of done says what every item must have before anyone calls it finished, whatever the story. Teams that mix the two either repeat "reviewed and documented" under every story, or forget it under all of them. Picture two layers: a bar every item clears, and each story's own criteria standing on top of it.

LivePer story versus every story3 min▶

The Agile Alliance glossary defines the definition of done as a list of criteria that must be met before an increment is considered done. Its history is short and telling: in 2002 Bill Wake raised the problem that "done" meant different things to different people; by 2007 the practice was widespread. Its main pitfall is the one you would guess: a definition of done that is not written down loses most of its value, because everyone carries their own.

The common practitioner reading is that the definition of done applies to every item, and acceptance criteria belong to one story. Be clear that this distinction is the practice, not a sentence on the glossary page: the page defines the definition of done without comparing it with acceptance criteria. It is still the reading that keeps specs short. "Shows last week's rate" belongs under story 1. "Source and owner named" belongs under every story, so it is written once, in the definition of done.

A useful test when you are unsure where a line goes: would it be true of the next story too? If yes, it is a definition-of-done line.

Self-studyA data product's definition of done3 min▶

Software teams' definitions of done often mention code review and deployment. A data product needs a few lines of its own, because its most common failures are about the data, not the code. A short version for Saffrondale (constructed):

★ Saffrondale definition of done (Constructed Saffrondale example)Definition of done (applies to every item): - Every metric on the page has a written definition, reviewed by the decision owner. - Every table used has a named source and a named data owner. - Freshness is monitored, and a late load alerts the data owner by 07:00. - The decision owner's sign-off is recorded with a date and a version.

Each line points to a later session: definitions, source and owner, and freshness are session 5; sign-off and versions are session 6. Write the definition of done once, near the top of the team's working agreement rather than inside one spec, and keep it to lines that really apply to every item. A definition of done with twenty lines gets skipped; one with four gets checked.

Real world

"Done" took years to mean one thing. The Agile Alliance glossary records the history of the definition of done: Bill Wake pointed out in 2002 that teams used "done" inconsistently, and by 2007 a written definition of done was widespread practice. The fix was not a cleverer word; it was writing the list down where everyone could see it (Agile Alliance, Glossary: Definition of Done, agilealliance.org).

Homework

Before session 4

30 min
  1. Write criteria for your own ask. Take the decision statement and stories you wrote after sessions 1 and 2. Write one Given, When, Then scenario for the most important story, and at least one measurable bullet for each of the others.
  2. Add three non-functional lines. One for freshness (an age and a deadline), one for speed (a time and a load), one for access (who sees what). For each, write the check a builder would run.
  3. Find one rule. Pick a business rule hidden in your metric, like Saffrondale's 24-hour cancellation rule. Write it with two examples, one on each side of the edge.
  4. Draft a four-line definition of done for your team's data products. For each line, ask whether it is true of every item. If it is not, move it under a story as an acceptance criterion.
Check yourself

Three questions

Clear all three and session 3 gets stamped in your passport.

1 · Which Then line can a builder test?

C names an outcome the user can observe: a rate, for a clinic, over a stated week. A and D give nothing to look at or count. B can be checked by someone, but it is a hidden internal; the Gherkin reference advises verifying what the user can observe instead.

2 · Why is Mars Climate Orbiter a verification story rather than a missing-requirement story?

The Mishap Investigation Board found the requirement in the interface specification; the trajectory modelers even assumed metric "per the requirements". What failed was the check of the delivered file. Acceptance criteria exist so that every written requirement gets one.

3 · "Every table used has a named source and a named data owner." Where does this line belong?

Acceptance criteria are per story; the definition of done is one list every item must meet. The per-story versus every-item split is the common practitioner reading; the Agile Alliance glossary defines the definition of done without making that comparison itself.
