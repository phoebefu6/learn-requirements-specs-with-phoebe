Learn Requirements & Specs with Phoebe

User stories, acceptance criteria and a spec a builder can act on, for the data product you are not coding yourself. Turn a one-line ask into a one-page spec with zero open questions. A spec is finished when the builder has no questions left, so every session asks the same two things: how many questions would a builder have to ask before starting, and which of them would they quietly guess instead? One running case throughout, Saffrondale Clinics, a constructed network of six outpatient clinics that asked for "a no-show dashboard, and maybe a model", and a real spec checker in the browser that turns every gap into the question it forces.

The six sessions 🎯 · from a one-line ask to a signed one-page spec

The running case is Saffrondale Clinics, a constructed network of six outpatient clinics (no real patients, no real data). The operations director asks for "a no-show dashboard, and maybe a model". Each session adds one piece to Saffrondale's one-page spec: a decision statement, stories, criteria, a checked draft, a pinned-down metric, and a signature.

🎯 Session 1 · foundations

The ask behind "a dashboard, and maybe a model"

The decision a data product serves, who acts on it and what changes if it exists; the cost of a requirement the builder had to guess. Build-along: turn Saffrondale's one-line ask into a decision statement.

▶ Start here 👥 Session 2 · foundations

User stories that say who, what and why

The story format, INVEST, splitting, stories against tasks, and the honest argument over whether data work needs stories at all. Build-along: rewrite five vague stories.

who, what, why ✅ Session 3 · core

Acceptance criteria a builder can test

Given, When, Then; rule-based criteria; freshness, latency and access written as criteria; the definition of done. Build-along: criteria for the no-show dashboard.

checkable, not hopeful 🔍 Session 4 · bench night

The bench: spec checker

A real rule engine in your browser: every finding with its line number and the builder question it forces, base rates on 440 real user stories, and an "add more words" button that shows length is not precision.

★ the bench 📏 Session 5 · stretch

The data side: metric definitions, grain, freshness, sources

Numerator, denominator, filters, time window and grain; the "same name, two numbers" failure; freshness, source and owner; data cards for a model. Build-along: define the no-show rate so two analysts get one number.

one name, one number ✍️ Session 6 · capstone

The one-page spec, sign-off and change control

The one-page template, sign-off by the decision owner, versioned changes and what forces a re-sign. Capstone: Saffrondale's signed spec, scored on the checker.

Your passport 🎫

Clear all three quiz questions in a session and it gets stamped. Six stamps means you can find the decision behind an ask, write stories that say who, what and why, write criteria a builder can check, run a spec through a checker and read its findings, define a metric so two people get one number, and get a one-page spec signed and keep it signed. Choose your path 🗺️

Two doors into the same spec, one for each side of the handover, and a third for the whole route. The requester writes it; the builder reads it; both should be able to count its open questions.

📝 Requester path: I ask, someone else builds 1→ 2→ 4→ 6 name the decision, write the stories, check the draft, sign it
🛠️ Builder path: I receive the spec 3→ 4→ 5 turn hopes into checks, count the open questions, pin the metric down
🎯 The whole one-page spec 1→ 2→ 3→ 4→ 5→ 6 from one line to a signed page with zero open questions

What is honest here 🧾

The checker computes for real; the running case is constructed and labelled; frameworks are read at their source; contested advice is taught as a disagreement.
